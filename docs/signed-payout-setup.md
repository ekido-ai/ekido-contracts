# Signed payout setup (under development)

This describes the new passing-verdict path. It is not yet a production or testnet runbook: end-to-end validation is outstanding, failed-job verdict signing is refused, and old demo jobs do not contain the required terms. The contract's existing permissionless timeout refund remains available after its deadline and grace period.

The current client binding signs the job ID, chain, escrow, workload, policy and budget; it does **not** sign `deadline_seconds`. The coordinator records its deadline when the job is registered. Do not describe the duration as client-signed or enable a funding flow that assumes that it is. A protocol change would be needed to bind the duration cryptographically.

Each verifier must configure its own trusted `VERIFIER_RPC_URL`, `VERIFIER_CHAIN_ID` and `VERIFIER_ESCROW_ADDRESS`. Set `VERIFIER_STATE_DIR` to a private local directory if its signed final evaluation context must survive a restart. A verifier with missing configuration, missing evidence or an unavailable chain refuses to sign. Existing workers need to be restarted with these settings; never take these values from a coordinator's task.

The client and each provider use `experiments/prepare_signed_job.py` offline. It reads `CLIENT_PRIVATE_KEY` or `PROVIDER_PRIVATE_KEY` from that participant's own environment and prints a signed document; it does not contact other participants or submit transactions. Do not share private keys. Ensure `gpuchain_core` is installed or its package directory is on `PYTHONPATH`.

For a new real AG News experiment, first run `python experiments/prepare_identity.py --out experiments/identity_agnews.json` in an environment with `datasets` and `huggingface_hub`. This accesses Hugging Face and hashes the full ordered train and test splits; retain the resulting identity file and use it with the experiment's `--identity` option. Pin the workload before requesting provider quotes: changing revisions or hashes afterwards changes the signed workload. Historical checkpoint specs remain unchanged and can still be resumed using their original identity. The identity path and actual dataset have not yet been validated on GPU.

1. The client runs `ids --client <client-address>` and shares the resulting job ID, on-chain ID, chain ID, escrow address and proposed workload with providers.
2. Each provider runs `quote --job-id <id> --onchain-id <id> --chain-id <chain> --escrow <address> --provider-id <registered-id> --rate <usdc-per-step> --spec <workload.json>`. The quote binds the job, domain, rate and workload hash. Provider wallet consent currently supports EOA signatures, not contract wallets.
3. The client adds each quote to `workload.provider_terms` as an object with `provider_id`, `wallet`, `price_per_step` and `quote`. The wallet and rate must match the provider's registration and the quote. The coordinator only schedules agreed providers with matching current registration.
4. The client runs `bind --job-id <id> --onchain-id <id> --chain-id <chain> --escrow <address> --spec <workload-with-quotes.json> --policy <policy.json> --budget <usdc>`. Submit the normal `POST /jobs` body with the complete workload, policy, budget and deadline, plus `job_id`, `client_address` and the resulting `job_binding`. The same client must fund the resulting on-chain job. Creation validates and stores the binding; verifiers independently verify it against the actual escrow client.

For the website, use `request` in place of `bind` and add `--deadline-seconds <seconds>`. Paste the resulting JSON into **New job**. The website checks the signatures before registration. The operator token authorizes coordinator requests, and the client wallet authorizes the on-chain approval and funding separately. Save the JSON locally if you need to reopen the same job.

Use the same provider wallet that registered with `gpuchain_agent.join` when signing its quote. Set `PROVIDER_PRIVATE_KEY` on that provider machine for the offline quote command. The quote's provider ID is the ID printed by join.

The coordinator supplies signed manifests, wallet delegations and signed handover reports to the verifier, which checks them against its configured escrow and its own final report before deriving the payout. Historical worker keys without their wallet-signed delegation cannot be authenticated. Quorum decisions and pending verdict inputs are persisted. On restart, unexpired proposals are restored only when their stored verdict and configured domain match and the on-chain job is still Active; partial signatures are re-collected. An unavailable RPC is retried on later verifier claims. Expired proposals, already-attested settlements and in-flight evaluations are not yet automatically reconciled, so coordinator restart is not a complete durable recovery path. An unfinished evaluation claim expires after 180 seconds and an unsigned verdict claim after 30 seconds; a submitted report or signature is not reclaimed.

The secure worker does not sign failed-job refund verdicts. For an eligible Funded/Active job, the contract permits anyone to trigger a client refund after its deadline plus grace period. `experiments/claim_timeout_refund.py --rpc-url <trusted-rpc> --chain-id <id> --escrow <address> --job-id <onchain-id>` only checks status by default. Adding `--submit` uses `REFUND_CALLER_KEY` to send a transaction; it credits the on-chain client, who must separately withdraw. Verify the chain, address and job before opting in. This fallback does not establish that a job failed and does not replace a reviewed early-failure protocol.

`--unsafe-local-demo-verdicts` deliberately restores coordinator-trusting behavior only for proposed chain ID 31337. It is insecure and is intended solely for local synthetic regression tests, never funds of value. The normal demo launcher does not enable it automatically.
